- **`dws aitable record create` gains `--parent-record-id`** — an optional entry point for creating hierarchy sub-records under a parent record, alongside the existing `dws aitable record create-sub` command. Both flags (`--parent-record-id` and optional `--view-id`) simply add the optional `parentRecordId`/`viewId` properties to the same pinned `create_records` RPC — the MCP server routes to hierarchy creation internally — so the command stays a single parameter-equivalent `create_records` projection. Sub-record-only flags are rejected without `--parent-record-id`, the 100-record limit is enforced client-side, and plain creation is byte-for-byte unchanged.
- **Response shape (verified end-to-end against the shipped MCP server, including a team table that already had hierarchy configured)** — sub-record creation returns `data.newRecordIds[]` (same key as plain creation) plus `data.hierarchyFieldId` and `data.parentRecordId`. `data.viewId` is echoed whenever the table already has a view carrying `hierarchyConfig` (it is that view's id), and is absent **only** on the very call that auto-creates the hierarchy field, so consumers must not assert it as a required field.
- **Hierarchy field shape and read-side contract (measured, documented in the skills references)** — the first sub-record call on an unconfigured table adds exactly **one** self-referencing field (`父记录`, `type=unidirectionalLink`, `config.linkedTableId` = the same table, `multiple=true`), not a bidirectional pair; a table that already has one reuses it with zero schema change. The link lives on the child, so the parent's cells carry no back-reference; query a parent's children with `record list --filters` using `any_of` on the hierarchy field with the parent ID in an array (`contain`/`eq` silently match zero rows instead of erroring), which returns **direct** children only — a grandchild needs a recursive walk. Test "is a sub-record" with `exist`. Updating other fields on a child preserves the link, and deleting a parent does **not** cascade — children keep a dangling `linkedRecordIds` entry. The hierarchy field id itself is discoverable three ways (all verified to agree): `view get` → `custom.hierarchyConfig.fieldId` (read-only, disambiguates when a table has several self-links), `field list` → `type=unidirectionalLink && config.linkedTableId==thisTable`, or the `data.hierarchyFieldId` echoed by a prior sub-record create.
- **`clientToken` deliberately not exposed** — `create_records` also accepts an optional UUID v4 `clientToken` idempotency key (a repeated request with the same token is rejected as a duplicate rather than silently deduplicated). No flag is added for it here: the create path already avoids retries (`callMCPTool`, not the retrying wrapper), so surfacing a dedupe key without a retry-on-timeout story would only create a new way to fail.

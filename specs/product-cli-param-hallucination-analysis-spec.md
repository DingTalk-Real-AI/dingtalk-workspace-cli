# 产品 CLI 参数问题分析与兜底改造 Spec

## 1. 目的

本 Spec 用于重复分析任意一个 DWS 产品的参数体系，判断哪些问题可能导致 Agent 生成错误参数或产生参数幻觉，并给出当前 `internal/cli/param_concepts.json` 能否处理、应如何处理以及暂时处理不了什么。

最终交付必须直接回答三个问题：

1. 这个产品有哪些参数问题；
2. 每个问题影响哪些具体命令和参数；
3. 现有参数兜底能力能否解决，应该如何配置。

交付是面向评审和汇报的产品分析，不是把内部审计数据原样导出。

## 2. 分析范围

### 2.1 必须分析

- 当前真实可执行命令和参数；
- 从同一提交重新构建后，由运行时组装 Schema 发布的命令参数；
- 产品 Skill 中描述的命令参数；
- 同一个业务实体在不同命令中的参数名称；
- 相同参数名在不同命令中的实际含义；
- 单个值与多个值的差异；
- 相似标识符的值域差异，例如 userId 与 openDingTalkId；
- 参数承担的业务角色，例如发送者、接收者、新群主、被引用消息；
- 当前 `param_concepts.json` 的 concept、命令范围、命令级别名和保护配置。

### 2.2 默认不分析

- 历史实验 badcase；
- `dws-eval`、`merged_scan.json` 或历史评测工作簿；
- 参数出现次数、模型通过率或线上频次；
- 底层接口字段的改名；
- 通过修改 CLI 真实参数来强制统一所有命令。
- 用户自定义 Shortcut、已安装插件等本机运行时扩展；除非任务明确要求，
  它们不进入官方产品参数基线。

如果后续需要结合实验数据，应单独形成观察样本附录，不能替代产品参数事实。

## 3. 事实来源

每个产品至少检查以下来源：

1. 从目标提交重新构建的二进制所提供的真实
   `dws <product> ... --help`；
2. 同一二进制运行时组装的 `dws schema <product>`；必要时可使用
   `cmd_schema_catalog` 导出一次性 CI/本地审计文件，但不得把该文件当成
   提交态生产 Schema 来源；
3. 产品 Skill；
4. `NewSchemaSourceRootCommand()` 构建的官方命令树，以及
   `schema_command_exclusions.go` 中明确排除的兼容命令和快捷命令；
5. 当前 `internal/cli/param_concepts.json`；
6. 必要时查看命令实现，确认参数最终表达的业务含义。

发生不一致时，按以下顺序判断：

```text
同一提交的真实 --help / Cobra 可接受参数
  > 同一提交运行时组装的 Schema
  > 产品 Skill
  > 当前参数兜底配置
```

别名表只能把一个非真实参数名归一到该命令已经存在的真实参数，不能创造新的真实参数，也不能证明两个参数在业务上天然等价。

### 3.1 当前 Schema 与参数兜底链路边界

当前 Schema 采用“声明即 Catalog”的运行时组装方式：

```text
当前提交中的 leaf Contract / ProductDecl / Cobra flags
  ↓ NewSchemaSourceRootCommand
官方 distribution-owned Cobra 命令树
  ↓ CollectIdentitySpecs / BuildEffectiveCommandRegistry / Bind
ResolveSchemaBuild
  ↓
运行时 SchemaRegistry
  ↓
dws schema 查询（进程内首次组装并缓存）
```

分析时必须遵守以下边界：

1. “运行时组装”表示从当前二进制内的声明组装，不表示实时读取工作区源码、
   远程 MCP 或用户目录；源码变更后必须重新构建二进制；
2. 官方 Schema 根不加载用户自定义 Shortcut 和已安装插件；仓库内置 Shortcut
   属于正式产品面，必须纳入；
3. 不再读取或提交 `schema_catalog.json`、`schema_catalog/` 或 Schema meta-index
   作为生产事实来源；`cmd_schema_catalog` 只用于一次性审计与确定性检查；
4. Schema 发布的是当前命令真正接受的 canonical flags 及其声明语义，不能据此
   推断 `param_concepts.json` 中的中央别名已经生效；
5. 参数兜底仍由 `param_concepts.json` 经 `go generate ./internal/cli` 生成
   `param_aliases_generated.go`，随后由 `RunPreParse` 在 Cobra 解析前执行；
6. Schema 与参数别名生成器应使用同一个 `NewSchemaSourceRootCommand()` 官方
   命令树。分析和测试必须同时验证“Schema/Help 参数事实”与“PreParse 别名行为”。

## 4. 需要识别的参数问题

分析时至少检查以下问题，但最终汇报应按产品实际情况合并，不要求每类单独建表。

### 4.1 同一个实体使用不同参数名

例如同一个开放会话 ID 在不同命令中使用：

```text
--group
--id
--chat
--conversation-id
--open-conversation-id
```

这种情况容易让 Agent 根据其他命令经验生成当前命令不接受的参数名。

### 4.2 相同参数名表示不同含义

例如 `--group` 在某些命令中表示开放会话 ID，在另一些快捷命令中表示群名称关键词。

这类问题不能配置全局别名，只能按精确命令处理。

### 4.3 相似名称实际属于不同值域

例如：

- 数字群号与开放会话 ID；
- userId 与 openDingTalkId；
- robotCode 与 openBotId；
- openMessageId 与 openTaskId。

值域不同的参数必须拆开，不能因为名称近似而互相兜底。

### 4.4 单值和多值混用

例如 `--user` 有时接收一个用户，有时接收逗号分隔的多个用户；`--users` 在不同命令中又可能接收不同类型的用户标识。

单值与多值默认不能自动互转。

### 4.5 参数角色不清楚

例如发送者、接收者、新群主和被引用消息虽然都是某类 ID，但角色不同。通用 `--user-id` 或 `--message-id` 不应覆盖这些角色差异。

### 4.6 Schema、Help 和 Skill 不一致

至少检查：

- Skill 写了当前命令不存在的参数；
- Skill 漏写真实参数；
- 稳定命令在 Skill 中缺少精确参数说明；
- Skill 是否把原生兼容参数误写成中央别名能力。

这类问题应修改参数文档来源，不应伪装成别名表问题。

## 5. 兜底结论

每个参数问题必须归入以下一种或多种处理方式，并使用中文展示：

| 处理方式 | 适用情况 |
|---|---|
| 增加概念别名 | 同一实体、同一角色、同为单值或同为多值，参数值可以原样传递 |
| 增加命令级别名 | 只有在特定命令中才能确认来源参数和目标参数等价 |
| 绑定宽泛真实参数 | 当前真实参数名过于宽泛，例如 `--id`，需要在精确命令中声明它代表什么概念 |
| 安全拦截 | 参数名看似接近，但值域、角色或单复数不一致，自动转换可能造成错误操作 |
| 提示歧义 | 同一命令存在多个合理目标，系统不能安全判断应映射到哪个参数 |
| 保持原生行为 | 来源参数本身已经是命令真实接受的兼容参数，不再经过中央别名重写 |
| 修改 Skill/Schema 来源 | 问题属于公开参数契约不一致 |
| 当前能力不支持 | 需要查询、修改参数值、拆分参数、合并参数或改变单复数 |
| 无需处理 | 参数名称、含义和值域已经清楚 |

### 5.1 自动别名的准入条件

只有同时满足以下条件，才能配置自动别名：

1. 来源参数不是当前命令的真实参数；
2. 目标参数是当前命令真实接受的参数；
3. 两者表示同一个业务实体；
4. 业务角色相同；
5. 都是单值或都是多值；
6. 值域相同；
7. 参数值可以不做修改直接传递；
8. 不需要先调用另一个命令查询；
9. 不会绕过必填、互斥或命令自身校验；
10. 配置被限制在已经审核过的命令范围内。

任一条件不满足，就应保留原生行为、拦截、提示歧义或列为当前不支持。

## 6. 分析流程

### 第一步：冻结分析基线并盘点产品命令

记录分支和 commit，从该提交重新构建临时二进制。合并运行时组装 Schema
命令、官方命令树、审核排除项、兼容命令、内置快捷命令和可执行父命令，
形成精确命令清单。不得直接信任来源不明或由其他分支构建的现有 `./dws`。

### 第二步：对账公开参数

使用同一提交、同一官方命令树逐命令比较真实 Help、完整 Schema leaf 和
Skill，先找出不存在、漏写或描述不一致的参数。`--compact` 可用于选参概览，
参数类型、必填、约束、property 和 provenance 审计应读取完整 leaf 或
`schema --all` 的对应工具，不能只看 compact 摘要。

### 第三步：按业务实体归并参数

把参数归入会话、消息、用户、机器人等业务实体，再检查名称、值域、角色和单复数是否一致。

### 第四步：形成参数问题

相同根因必须聚合为一个易读的问题。例如“用户标识符命名、单复数和值域混杂”可以包含多个具体命令，但不应为了内部维度拆成多个汇报问题。

### 第五步：映射到兜底能力

对每个问题判断：

- 能否增加 concept；
- 是否只能增加命令级别名；
- 是否需要绑定宽泛参数；
- 是否需要 block/ambiguous；
- 是否应该保持原生；
- 是否属于 Skill/Schema 修复；
- 是否超出当前链路能力。

### 第六步：生成产品候选别名表草稿

在完成问题分析和兜底判断后，必须基于当前正式
`internal/cli/param_concepts.json` 生成一份完整候选文件，保存到：

```text
docs/parameter-hallucination/<product>/param_concepts.json
```

例如 Doc 产品保存为：

```text
docs/parameter-hallucination/doc/param_concepts.json
```

候选文件必须满足：

1. 是当前正式别名表的完整副本加本产品改动，不是只包含新增规则的片段；
2. 不直接修改 `internal/cli/param_concepts.json`；
3. 非目标产品的 concept、command override 和保护规则保持不变；
4. 已有 concept 可以追加本产品的精确命令范围，但不能借机扩大其他产品范围；
5. 新规则必须能回溯到 Excel/Markdown 中的具体问题和命令；
6. 无法安全自动转换的情况写入 block/ambiguous 或不进入候选表，不能为了提高
   覆盖率强行配置 alias；
7. 保持正式文件的结构和可读格式：每个 concept、command override 和 fixture
   尽量单行展示，便于人工 diff；
8. 候选文件是待审核草稿，不得在未验证时标记为可以直接替换正式表。

### 第七步：审核候选草稿是否合理正确

生成候选表后必须进行一次独立的修改审核，不能只验证 JSON 能否解析。至少检查：

1. 对比正式文件，确认改动只服务于目标产品和本轮已确认的问题；
2. 每条自动 alias 的来源不是当前命令已经具有不同语义的真实 flag；
3. 目标参数是该精确命令真实接受的 canonical flag；
4. 来源和目标属于同一业务实体、同一角色、同一值域、同一单位，并且同为单值
   或同为多值；
5. 参数值可以原样传递，不需要查询、拆分、合并、JSON 包装、类型转换或单位转换；
6. 命令路径存在于同提交的官方命令树，且不会误命中可执行父命令、其他产品命令、
   用户自定义 Shortcut 或插件；
7. concept 的 `commands`、`members` 和 `excludes` 是否足够收敛，command override
   是否应该使用 `scope_strict`、block 或 ambiguous；
8. 是否重复实现了命令自身已有的隐藏兼容 flag；如果保留重复覆盖，必须说明统一
   进入中央治理的收益；
9. 新增规则数量和影响命令数是否异常膨胀；出现大范围 alias/block 时必须抽样复核
   并在报告中说明影响面；
10. 所有无法确认的映射从草稿中移除，转入“当前无法解决”或待人工确认清单。

审核结果必须在 Markdown 和 Excel 的“兜底解决方案/分析依据”中说明，至少区分：

- 已审核且建议落地；
- 规则合理，但落地前仍需补测试；
- 审核后移除或暂不支持。

### 第八步：验证候选草稿

将候选文件临时放入独立分析副本或临时 worktree 的正式输入位置，验证别名来源、
目标和保护规则能够经过真实生成与 PreParse 链路。不得为了测试直接覆盖当前工作区
的正式 `internal/cli/param_concepts.json`。

验证至少包含：

- JSON Schema/生成器能够读取候选文件；
- 生成结果与候选配置一致，且生成物确定；
- alias 输入与 canonical 输入进入相同最终参数或 payload；
- block/ambiguous 在 dispatch 前终止；
- 原生命令参数、其他产品规则和非目标流程没有回归；
- 写操作使用 dry-run 或注入 Runner，不能发起真实业务写调用；
- 如果仓库政策要求新增 complete-command payload 模板，必须补齐后才能把候选标记
  为可直接合并。

若完整测试没有通过，候选文件仍可作为分析草稿交付，但必须明确列出失败项、原因和
正式替换前需要补充的代码或测试，不能表述为“已经验证通过”。

## 7. Excel 汇报要求

工作簿只保留五个页面，页面和列名全部使用中文。

### 7.1 `汇报总览`

一行表示一个聚合后的参数问题，至少包含：

```text
问题名称
问题现象
涉及命令数
主要风险
现有兜底能力结论
推荐处理
优先级
```

总览不展示内部编号、内部问题族、英文状态码、实验次数或大量为零的统计字段。

### 7.2 `参数问题明细`

一行表示“一个参数问题在一个具体命令上的表现”。同一命令同一问题下的多个参数应合并展示。

```text
问题名称
命令
当前参数
参数实际含义
为什么容易出错
建议处理
现有兜底结论
证据来源
```

该页面用于回答“这个问题到底涉及哪些命令和参数”。

### 7.3 `兜底解决方案`

一行表示一个可执行的治理动作：

```text
治理对象
准备解决的问题
建议配置
适用命令
处理方式
现有功能能否完成
验证重点
优先级
```

需要出现 JSON concept 名称时可以保留英文标识，但说明和结论必须使用中文。

### 7.4 `当前无法解决`

只列现有别名表确实做不了或不应该做的事项：

```text
场景
涉及命令
为什么别名表不能处理
当前安全做法
如果未来要支持需要什么能力
是否阻塞第一轮治理
```

### 7.5 `分析依据`

简要记录产品、分支、commit、构建方式、Schema `source`、官方命令树边界、
命令覆盖和实际使用的 Schema、Help、Skill、concept 来源，并明确声明未使用
实验结果、历史固定 Catalog、用户自定义 Shortcut 或插件。

## 8. Markdown 报告要求

报告应与 Excel 使用同一组聚合问题，至少包含：

1. 结论摘要；
2. 每个参数问题的现象、风险和解决方式；
3. 当前别名表可以直接实施的方案；
4. 当前能力支持不了的事项；
5. 第一轮改造建议；
6. 产品候选 `param_concepts.json` 相对正式文件的改动摘要、影响范围和审核结论；
7. 候选草稿的验证结果、尚未通过的门禁及正式替换前置条件；
8. 可复用到其他产品的分析流程。

完整命令列表放在 Excel，Markdown 只展示代表命令和关键结论，避免重复粘贴大表。

## 9. 验证要求

生成产品候选 `param_concepts.json` 后，应在独立分析副本或临时 worktree 中把候选
文件临时作为正式输入，至少执行：

```bash
jq empty docs/parameter-hallucination/<product>/param_concepts.json
# 仅在独立分析副本或临时 worktree 中执行下一行
cp docs/parameter-hallucination/<product>/param_concepts.json internal/cli/param_concepts.json
go generate ./internal/cli
DWS_PACKAGE_VERSION=0.0.0-test go test ./internal/cli ./internal/pipeline ./internal/app
./scripts/policy/check-generated-drift.sh
./scripts/policy/check-schema-catalog.sh
```

执行前后还必须保存并审核“正式文件 → 产品候选文件”的结构化 diff，统计新增或
修改的 concept、command override、实际生成 alias、block 和 ambiguous 数量。
仅通过 `jq empty`、生成器或数量断言，不能证明映射在业务语义上正确。

其中 `make generate-schema` 只刷新参数别名等生成物并验证 Schema 组装确定性；
它不生成或更新一份提交到仓库、供生产读取的固定 Catalog。

行为验证至少覆盖：

- 别名输入与真实参数输入进入同一个最终参数；
- block/ambiguous 在命令执行前给出明确提示；
- 原生真实参数继续由 Cobra 正常解析；
- 单值不会静默变成多值；
- 不同值域不会只通过改名互相传递；
- Skill 中不再出现当前命令不存在的参数；
- 非目标产品的有效别名和最终 payload 不发生变化；
- 候选草稿中的每项新增规则都能关联到分析明细和审核结论。

## 10. 验收标准

交付满足以下条件即可完成：

1. 用户能从总览直接看出产品有哪些参数问题；
2. 每个问题都能下钻到具体命令和参数；
3. 每个问题都有明确的兜底结论和建议；
4. 能通过现有别名表完成的方案足够具体；
5. 当前能力做不了的事项单独说明原因和安全处理；
6. 页面和字段使用中文，不出现内部编号和无意义的零值统计；
7. 分析只基于当前产品事实，不混入未指定的实验数据；
8. 在 `docs/parameter-hallucination/<product>/param_concepts.json` 生成了基于正式
   别名表的完整候选草稿，正式文件没有被直接修改；
9. 候选草稿完成了命令、值域、角色、单复数、单位、真实 flag 冲突、影响范围和
   原生兼容重复等审核；

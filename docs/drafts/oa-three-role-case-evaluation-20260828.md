## 一、输入与口径

本报告合并以下评测产物：

1. `oa_simple_main_two_pass_business_evaluation_20260825.zip`：符咏畅发起人场景，两轮独立运行。
2. `audit_20260825_192919_oa_approver_nanrun_multi_c1_stagger3_kf_run1.zip`：南润审批人 Multi 场景。
3. `OA柏智双Suite评测报告包_20260827_152535_160238.zip`：柏智审批人 Mono 与抄送人 Multi 场景。

三个包使用了不同的业务 Judge、task-completion 和人工复核口径，远端审批初始状态也不一致，因此：

- 保留每个报告的原始判定词，不把 `success`、`blocked`、`未完成` 强行换算成同一种分数。
- 不合并计算一个总成功率。
- 废弃无评分配置却固定输出 100 分的 checkpoint 结果。
- 以 Query、实际命令与返回、最终答复和人工轨迹复核为主要证据。

## 七、跨角色共性问题

### P0：业务对象身份必须可证明

角色来源是对象身份的一部分：

- 发起人对象来自创建成功回执或“我发起的”列表。
- 审批人对象来自“待我处理”列表及当前任务。
- 抄送人对象来自 `list-cc`。
- 管理员对象只在明确管理员意图且具备权限时来自 `list-by-admin`。

后续 `detail`、评论或附件接口能访问该实例，只能证明“对象可访问”，不能证明它属于用户要求的角色关系。

### P0：写操作前后都要验证业务不变量

执行前核对角色来源、流程名、发起人、状态、实例 ID、任务 ID、核心字段和用户前提；执行后核对真实成功字段与状态变化。目标不匹配、前提检查失败或写后无法验证时，必须报告未完成。

### P1：查询应基于证据收敛，不宜固定“最多两次”

建议规则：

> 定向找单时，先在用户指定的角色来源内查询。若返回明确空结果，可做一次有依据的条件放宽；若仍明确为空则停止。存在 `hasMore`、`nextCursor` 或总数证据时按需分页。不得穷举同义词，也不得切换角色来源寻找替代对象。

这比“空结果最多两次查询”更稳妥：既能限制无界探索，也不会误伤有分页证据、用户要求完整列表或关键词需要合理放宽的场景。

### P1：区分空结果、参数错误和业务错误

- 空结果：按范围完整性证据决定是否放宽或结束。
- 明确参数错误：允许纠正一次。
- 重复或不可重试业务错误：停止参数变体尝试，如实交付失败。
- 超时或上游未知错误：不能声称业务成功，必须保留最终答复时间。

### P1：发起审批需要模板专项处理

通用审批两轮成功，而请假、报销、用车和物品领用持续失败，说明问题不只是命令发现，而是复杂控件、明细字段和模板后端能力差异。发起审批应按需加载创建专项说明，不应让所有 OA 查询任务承担完整创建上下文。

### P2：完整查询与 Token 控制需要同时成立

不能为省 Token 省略 `hasMore` 分页、用户要求的全部表单或关键字段；可以通过以下方式降低浪费：

1. 候选定位阶段只保留必要字段，选中后再读取完整详情。
2. 删除 OA reference 中命令总览、意图表、核心工作流和注意事项的重复说明。
3. 将发起审批、附件操作拆成按需 reference，普通查询不加载。
4. 对空结果和重复业务错误及时收敛，避免 10～30 次无效调用。

## 八、已实施的 Skill 设计修复

| 方向 | 实施结果 |
|---|---|
| 角色来源 | 将 pending、cc、submitted/initiated、executed、admin 定义为不可静默互换的对象来源 |
| 查询收敛 | 移除“固定最多两次”，改为根据空结果和分页证据做有依据的放宽与 endpoint exhaustion |
| 写操作闭环 | 增加流程、发起人、状态、实例/任务 ID、业务前提核对和写后回读 |
| 错误处理 | 区分空结果、参数错误、权限错误和 retryable 业务错误；参数变体不重置预算 |
| 特殊控件 | 将缺少稳定契约的 `DDHolidayField` 标为不可猜测提交，禁止用真实审批试探 payload |
| Progressive disclosure | 将约 67KB 的 OA 核心 reference 收敛到约 11KB；创建和附件改为按需专项加载，删除旧 Skill 摘要等重复内容 |

3. 用新 fixture 复跑 Multi，验证角色来源、空结果收敛和最终交付是否生效。
